## 一、执行摘要

1. **项目要解决的问题**：公司内部办公文件（Word/Excel/PPT）外发后无法管控。目标是做到"文件落盘即密文、从磁盘拷走/发邮件/发微信拿到的都是密文、非授权软件打不开"。
2. **技术路线**：复用公司现有的 LibreOffice 自定义加密引擎（`lo-encryption-demo`，AES-256-CBC + PBKDF2，已跑通），在其外围补齐"无感注入 + 受控打开 + 中心密钥/审计 + 部署"四层。**不重写加密算法，不自研 Office 解析器**。
3. **当前状态**：方案已通过 24 轮双评审定稿（27 个实现任务 + 4 个终验任务，分 6 个阶段）；原型阶段已完成 4 项关键技术验证中的 **2 项全部通过、1 项推翻原假设（利好）、2 项待重做**。
4. **投资结论**：
   - **AI/Token 费用可精确测算**：已完成部分实测消耗 **2.07 亿 tokens**（含缓存命中 1.92 亿），按平台计费口径已花 **$38.6**；剩余 30 项任务预计再消耗约 **1.8 亿 tokens**。若改用国产一线模型官方直连价，全项目 token 成本仅 **¥80 ～ ¥2,400**（视模型档位）。
   - **真正的成本是人力与硬件**：按 1.5–4 人月估算，项目总投入 **¥10.6 万 ～ ¥33 万**（三档方案见第六章）。
   - **AI 费用占比 <2%**，属于可忽略量级；立项决策应聚焦"人力投入与业务收益"，而不是模型费用。

## 二、项目背景与目标

### 2.1 业务痛点

| 痛点 | 现状 | 期望 |
|------|------|------|
| 文件外发失控 | 员工把 docx/xlsx 直接发微信/邮件，发出即失控 | 发出的永远是密文，对方打不开 |
| 介质丢失 | U 盘/笔记本丢失后文件可被直接读取 | 卷未挂载时整盘为密文 |
| 无审计 | 谁在什么时候把什么文件另存/导出，无记录 | 全部加解密与外发动作留痕、可追溯、防篡改 |
| 密钥管理 | 无统一密钥，靠个人口令 | 公司统一主密钥 + 服务器集中签发/轮换 |

### 2.2 目标与边界（已与业务方确认）

**做**：
- OOXML 三格式（docx/xlsx/pptx）文件级透明加密
- `S:` 保密盘（VeraCrypt 卷）内落盘即密文
- 双击密文 → 受控打开 → 关闭自动重加密
- 另存为/导出/打印/发送 → 强制审计（仅记录，不审批）
- 中心服务器：主密钥签发/轮换、审计留痕（HMAC 哈希链防篡改）

**不做**（明确排除，避免虚假承诺）：
- 复制内容粘贴、手机拍屏、员工恶意规避（需内核级 minifilter，属采购范畴）
- 审批流（本期仅记录）
- 存量文件全量重加密扫描（forward-only）
- 审计整库文件级回滚检测

## 三、技术方案（已定稿）

### 3.1 架构

```
┌─────────────── 员工电脑（Windows） ───────────────┐
│  LibreOffice（默认/服务/受控 三套独立 profile）      │
│   ├─ 加密引擎 cipherbox.py（复用现有，AES-256-CBC）  │
│   └─ 强制加密拦截器（受控 profile 内驻留）           │
│  CipherBox Agent（Python）                          │
│   ├─ 文件夹监控 → 自动加密（UNO 通道）               │
│   ├─ 受控打开（解密→GUI→关闭→重加密，串行化）        │
│   ├─ 密钥缓存（DPAPI）/审计上报                      │
│   └─ `.cbx` 文件关联 + 启动器                       │
│  VeraCrypt 卷（S:，原版，零二次开发）                │
└──────────────┬──────────────────────────────────┘
               │ HTTPS（自签 CA + 证书 pin）
┌──────────────▼──────────────────────────────────┐
│  局域网服务器（FastAPI + SQLite）                   │
│   ├─ 员工令牌（TTL 90 天 / 续期 / 吊销）             │
│   ├─ 主密钥版本集签发与轮换（≥256bit 高熵）          │
│   └─ 审计事件（行级 HMAC + 链头锚点）                │
└─────────────────────────────────────────────────┘
```

### 3.2 关键技术选择及依据

| 选择 | 理由 |
|------|------|
| 复用现有 LO 加密引擎，不改算法 | 已通过真实文档回环验证；改造风险最低 |
| 主密钥直接作为"口令"喂引擎 | 复用已验证的口令派生 + verifier 校验路径 |
| 密文命名 `<原名>.cbx` | 保留原始扩展名，双击可关联启动器 |
| UNO 走**命名管道**（非 TCP） | loopback TCP 跨用户无认证；管道受用户 SID 隔离（已实测：`\\.\pipe\OSL_PIPE_<SID>_...`） |
| 受控打开用 **Agent 侧自行解密** | 绕开 LO 引擎 decrypt 在 `%TEMP%` 留明文临时文件的风险 |
| 解密后明文临时文件放卷内 | 卷卸载即不可读 |
| 审计用 HMAC 链 + 运行式链头锚点 | 防行级篡改与尾部删除 |

### 4.1 计划评审：已完成

### 4.2 技术验证（Wave 0，4 项）

| # | 验证项 | 结果 | 说明 |
|---|--------|------|------|
| 1 | 常驻管道服务 + 引擎注册 | ✅ **通过**（已验证） | 命名管道连通性实测 145ms；服务 profile 落卷内；幂等启动、超时保护、员工 LO 共存均验证 |
| 2 | UNO 重加密 + 格式边界 | ✅ **通过（并推翻一项计划假设）** | OOXML 三格式重加密回环全绿（45 项断言）；**重大发现：doc/xls/ppt 带加密数据时同样走自定义引擎**（原计划判断为"不走"，依据是仅口令路径的现象）→ 实际覆盖范围比预想更大 |
| 3 | 受控打开闭环 | ❌ **未交付** | 执行未产出工件，需重做（预计 1 个工作日） |
| 4 | LO 强制加密拦截器 | ❌ **未交付** | 同上 |

### 4.3 已发现的重大技术约束（影响方案，但不影响可行性）

**LO 26.8 的"自定义数据空间重载"路径不可用**（源码级定位：`decrypt()` 的 `[out]` 参数与 filterdetect 自嗅探机制不兼容）。

- 影响：**不能用 LO 直接打开 `.cbx`**（引擎虽被正确调用并解密成功，但 oox 层最终回退到 Text 过滤器）。
- 不影响生产链路：设计上受控打开由 Agent 侧自行解密（从不依赖 LO 重载），自动加密为"明文加载 + 加密保存"（已实测全绿）。
- 需调整：原计划中"用口令重载 `.cbx` 读回原文"这条验收口径需改为"引擎 API 级解密回环"。

### 4.4 完成度

- 计划任务：**1 / 31 完成**（管道服务），30 项待做（其中 2 项 spike 重做）。
- 代码产出：4 个 spike 脚本（1,029 行）+ 1 个服务启动器 + 3 个测试文件迁移 + 24 份证据工件。

## 七、可行性分析

### 7.1 技术可行性：**高**

| 关键点 | 证据 |
|--------|------|
| 加密引擎可用 | 现有引擎已通过真实文档回环（加密/解密/口令校验全部实测通过） |
| 无感加密可行 | 明文加载 + 加密保存路径全绿（45 项断言） |
| 命名管道通信可行 | 实测 145ms 连通，按用户 SID 隔离 |
| 受控打开可绕开 LO 限制 | 设计上由 Agent 自行解密，不依赖 LO 重载 |
| 审计防篡改可行 | HMAC 链 + 运行式链头锚点（设计已评审） |
| 部署可自动化 | PowerShell 脚本化（服务器引导/客户端安装/卷引导） |

### 7.2 组织可行性：**中高**

- 需要 IT 配合：VeraCrypt 卷、服务器、证书、开机自启策略
- 需要员工接受度：文件变成 `.cbx` 需双击打开，体验有变化 → 建议先小范围试点
- 需要明确责任人：密钥保管、服务器运维、审计查阅权限

### 7.3 经济可行性：**高**

- 对比采购商业透明加密/DLP 产品（通常 ¥500–1,500/人/年，50 人即 ¥2.5–7.5 万/年且持续付费）
- 自研一次性投入 ¥16.6 万，后续仅维护成本；核心引擎与依赖全部开源

## 九、结论与建议

### 9.1 结论
